# Releasing to the App Store and Google Play

What the code already covers, and the steps that need an account, a console or
a decision only the owner can make. Work through "Before the first release"
once; "Every release" is the routine after that.

## Already in the app

- **Identity:** display name `Locs`, bundle id / package `com.daez.locsapp`,
  icon, adaptive icon, splash and a monochrome Android notification icon, all
  generated from `assets/images/Locs_Icon.png`.
- **Versioning:** `eas.json` uses `appVersionSource: remote` with
  `autoIncrement` on production, so build numbers never collide. Bump
  `expo.version` in `app.json` for each user-facing release.
- **Permissions:** camera and photo library only (for event cover images), plus
  notifications. Microphone, overlay and legacy storage permissions are blocked
  on Android. `ITSAppUsesNonExemptEncryption` is `false`: the app only uses
  HTTPS, so no export-compliance paperwork is needed.
- **Accounts:** email, Google, and Sign in with Apple on iOS (Apple requires it
  whenever another social login is offered, guideline 4.8).
- **Legal:** Terms of Service and Privacy Policy, written once in
  `constants/legal.ts` and shown in the app (`app/legal/[doc].tsx`), on
  locsapp.net and as Markdown in `docs/`. New
  accounts must accept them; existing accounts are asked once.
- **Account deletion:** Settings → Delete account, which both stores require,
  and https://locsapp.net/delete-account for doing it without the app.
- **Links:** shared events are `https://locsapp.net/event/<id>`. With the app
  installed they open it (iOS universal links, Android App Links); without it
  the website sends people to their store. An event opened while signed out
  opens after login.
- **Email confirmation:** the confirmation link opens the app and signs the
  person in; on a computer, locsapp.net confirms the address instead.
- **Licensing:** the code is proprietary (`LICENSE`); open-source dependencies
  and their licences are listed in `THIRD_PARTY_NOTICES.md`. All are
  permissive (MIT, BSD, Apache-2.0, ISC; MPL-2.0 files are used unmodified).

## Before the first release

### 1. Publish locsapp.net (Cloudflare Pages)

The site lives in `web/` and is generated by `npm run web:build`. It serves the
home page, `/terms`, `/privacy`, `/delete-account`, the event link page, the
email confirmation page, and the two files that let links open the app
(`/.well-known/apple-app-site-association` and `/.well-known/assetlinks.json`).

1. Cloudflare dashboard → Workers & Pages → Create → Pages → **Direct Upload**,
   project name `locsapp` (the name `npm run web:deploy` uses).
2. From `Locs_app`: `npx wrangler login`, then `npm run web:deploy`.
3. In the Pages project → Custom domains, add `locsapp.net`. If the domain's DNS
   is not on Cloudflare yet, move its nameservers there first.
4. Check <https://locsapp.net/.well-known/assetlinks.json> returns JSON (not a
   redirect), and that <https://locsapp.net/event/test> shows the invite page.

Store listing URLs: privacy policy `https://locsapp.net/privacy`, account
deletion `https://locsapp.net/delete-account`, marketing `https://locsapp.net`.

Re-deploy whenever `constants/legal.ts` or `web/site.config.json` changes.

### 2. Email: send as locsapp.net with Resend

Supabase's built-in mailer only delivers to the project's own team, so real
users need a proper sender before email confirmation can be switched on.

1. resend.com → Domains → add `locsapp.net`, then add the DNS records it lists
   (in Cloudflare DNS) and wait for **Verified**.
2. Resend → API Keys → create one with sending access.
3. Supabase dashboard → Project Settings → Authentication → SMTP Settings:
   enable custom SMTP with host `smtp.resend.com`, port `465`, user `resend`,
   password = the API key, sender `no-reply@locsapp.net`, name `Locs`.
4. Authentication → URL Configuration: Site URL `https://locsapp.net`; Redirect
   URLs `https://locsapp.net/**` and `locs.com://**`.
5. Authentication → Emails → Confirm signup: subject "Confirm your Locs
   account", body = `locs_server/supabase/templates/confirmation.html`.
6. Authentication → Sign In / Providers → Email: turn on **Confirm email**.
   Also raise the email rate limit (Authentication → Rate Limits) above the
   default 2 per hour.

Steps 3–6 are also declared in `locs_server/supabase/config.toml` under
`[remotes.production]`: uncomment the SMTP block, set `enable_confirmations =
true`, and `RESEND_API_KEY=… npx supabase config push`. Run `npx supabase
config diff` first; note that a push of the auth section switches off the
unused Twilio SMS provider.

Do step 6 last: with confirmations on and no working sender, nobody can finish
signing up.

### 3. Link verification: store IDs

`web/site.config.json` holds what the association files need. Fill each in as
it becomes available, then `npm run web:deploy`:

- `appleTeamId`: Apple Developer → Membership → Team ID. Until it is set, iOS
  opens event links in Safari instead of the app.
- `appStoreId`: the numeric ID from App Store Connect → App Information. Until
  it is set, iPhone visitors see "App Store: coming soon".
- `androidSha256Fingerprints`: already holds the EAS signing key. After the
  first Play upload, add the **App signing key** SHA-256 from Play Console →
  Test and release → App integrity; Play re-signs the app with it.

Android re-checks App Links when the app is installed, so after changing the
fingerprints reinstall (or `adb shell pm verify-app-links --re-verify
com.daez.locsapp`) to test.

### 4. Google sign-in

1. In Google Cloud Console, create an OAuth client of type **Web application**.
   Add the Supabase callback as an authorised redirect URI:
   `https://uvlkjdvnyxgxlphvpjrg.supabase.co/auth/v1/callback`.
2. Supabase dashboard → Authentication → Providers → Google: enable it and
   paste the client ID and secret.
3. Redirect URLs are covered by step 2.4 above.
4. Configure the OAuth consent screen (app name, logo, privacy policy URL) and
   publish it, or only test users can sign in.

### 5. Sign in with Apple

1. Apple Developer → Identifiers → `com.daez.locsapp`: enable **Sign in with
   Apple**. (EAS does this on the next iOS build if you let it manage
   credentials.)
2. Supabase dashboard → Authentication → Providers → Apple: enable it and add
   `com.daez.locsapp` to the **Client IDs**. Native sign-in sends an identity
   token, so no Services ID or secret key is needed for the app itself.

### 6. Push notifications

- **Android:** create a Firebase project with the `com.daez.locsapp` Android
  app, then upload its FCM V1 service account key with
  `eas credentials -p android` → Google Service Account → Push Notifications.
  Without it, Android devices register but receive nothing.
- **iOS:** `eas build -p ios` creates the APNs key when asked.

The server sends pushes from Postgres through `pg_net`; no extra service runs.

### 7. Store listings

**Content rating.** Locs is a *simulated gambling* app: people stake virtual
coins on outcomes. Answer the rating questionnaires honestly:

The app is for adults: the Terms require users to be 18+, and sign-up asks
them to confirm it.

- App Store: "Simulated Gambling: Frequent/Intense", and set the age rating
  to **18+** (App Store Connect → App Information → Age Rating).
- Google Play (IARC): answer *yes* to simulated gambling, *no* to real-money
  gambling; in Target audience and content, select **18 and over** only. Coins can't be bought, sold or cashed out; say so in the review
  notes on both stores.

**App Store privacy labels / Play Data safety.** Data collected, all linked to
the account, none used for tracking or advertising, none sold:

| Data | Why |
|---|---|
| Email address | Account and sign-in |
| Name / user ID (username, Google or Apple ID) | Account, shown to other users |
| Photos (event cover images the user uploads) | App functionality |
| User content (events, questions, bets) | App functionality |
| Device ID (push notification token) | Notifications |

Data is encrypted in transit, and users can delete their account in the app.

**Review account.** Give the reviewers an email/password test account with some
coins and a few events, since Google and Apple sign-in are hard for them to use.

**Assets.** Phone screenshots for each store (iPad is off: `supportsTablet` is
`false`), a 512×512 icon and a 1024×500 feature graphic for Play.

## Test builds for iPhone testers

Both routes need a paid Apple Developer Program membership ($99/year).

**TestFlight (recommended).** Testers install Apple's TestFlight app and you
invite them by email or a public link; no device registration.

```bash
eas build -p ios --profile production --auto-submit
```

The first run asks for your Apple ID, creates the signing certificate and the
App Store Connect record, and uploads the build. Then in App Store Connect →
TestFlight: add internal testers (up to 100 people on your team, available as
soon as the build finishes processing) or an external group with a public
link (up to 10,000, after a short beta review).

**Ad hoc (`preview` profile).** Installs from a link like the Android APK, but
only on iPhones registered in advance, up to 100 a year:

```bash
eas device:create                 # share the link it prints; each tester opens it on their iPhone
eas build -p ios --profile preview
```

Register everyone before building; a new device needs a new build. The
`simulator` profile makes a build for the iOS Simulator on a Mac.

## Every release

```bash
eas build -p all --profile production
eas submit -p android --profile production   # internal track, see eas.json
eas submit -p ios --profile production
```

Apply any new `locs_server` migrations to the hosted database **before**
submitting, since the app calls those functions directly.
